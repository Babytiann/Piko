# PRD：首屏单接口与后端缓存

本文档约定 Piko 的「首屏数据/文案」下发方式，以及接口性能相关的缓存策略。

---

## 一、首屏单接口原则

### 原则

**一个页面的所有首屏文案都只通过一个接口下发；二级页另说。**

### 要求

- 每个一级页面（如首页、AI 页、个人主页）的首屏所需**全部文案与状态**，由该页的**唯一首屏接口**返回。
- 前端不得用多个接口（如鉴权接口 + 业务接口）拼首屏展示。
- 二级页（如设置、绑定、对话详情等）可单独接口，不要求与首屏共用一个接口。

### 对个人主页 (Profile) 的约束

- 个人主页首屏（Apple 登录区、关联账号、设置、退出等）的文案与登录态均由 **`POST /piko/profile/detail/v1`** 返回。
- 前端仅根据该接口响应驱动首屏，不再用 Better Auth 的 `useSession()` 单独驱动 Apple 登录区块。

---

## 二、前端请求方式（与参考仓库一致）

- **参考**：poi-reactlynx-next-rs 的「进页即请求、整页 loading」。
- **约定**：
  - 一页一个主请求，进入该页时再发请求，用整页 loading（如 `PageLoading`）覆盖等待过程。
  - **不做**跨 Tab 预取：不在根布局或 Tab 布局里预拉 Profile、AI 等非当前页数据。
  - **不引入** SWR/React Query 等做跨页预取；每页独立调自己的首屏接口即可。

---

## 三、后端缓存

### 目标

多用户访问同一类内容时，**相同的东西放缓存**，减少对数据库的重复访问（例如最基础的提示文案）。

### 可缓存内容

| 接口                        | 说明                                         | 缓存建议                                                              |
| --------------------------- | -------------------------------------------- | --------------------------------------------------------------------- |
| 首页 `homepage/summary/v1`  | 当前为静态文案，无 DB；若后续来自 DB/配置    | 对「首页文案」或接口响应做缓存，key 如 `home:summary`                 |
| AI 首屏 `ai/copywriting/v1` | 当前为静态文案；若后续来自 DB/配置           | 对文案或响应做缓存，key 如 `ai:copywriting`                           |
| Profile `profile/detail/v1` | copy 全员一致，仅 telegramSection 按用户不同 | 缓存 copy 或「未绑定」通用结构，按 userId 只算 telegramSection 后合并 |

### 缓存实现方式

- **可以接 Redis**：后端为 Node + Hono，可接入 Redis 做数据库/接口层缓存（如使用 `ioredis` 或 `@upstash/redis`，需配置 `REDIS_URL` 或 Upstash 等环境变量）。
- **建议节奏**：
  - 先用**进程内内存缓存**（如 TTL Map 或 LRU）落地，无需额外基础设施。
  - 需要多实例共享、或希望持久化/更大容量时，再接入 Redis；接口层对「读缓存 / 写缓存」做抽象，便于从内存实现切换到 Redis。

---

## 四、文档与技能引用

- 鉴权/登录相关逻辑以 Better Auth 文档与项目 PRD（如本文档及 `docs/PRD-Apple-Login-Better-Auth-Alignment.md` 若存在）为准。
- 前端实现时以「首屏单接口」与「进页即请求、整页 loading」为本 PRD 的强制约定。
